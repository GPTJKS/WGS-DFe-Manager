# PROMPT MESTRE — WGS DF-e MANAGER

## 1. VISÃO GERAL DO PROJETO

Desenvolver um sistema desktop privado para Windows destinado inicialmente ao uso interno de um escritório contábil brasileiro.

Nome provisório do projeto:

**WGS DF-e Manager**

O sistema será responsável por consultar, baixar, armazenar, organizar, pesquisar, validar, exportar e recuperar documentos fiscais eletrônicos — DF-e — de múltiplas empresas clientes do escritório.

Tipos de documentos inicialmente suportados:

* NF-e — modelo 55
* NFC-e — modelo 65
* CT-e — modelo 57
* CT-e OS — modelo 67
* NFCom — modelo 62

A aplicação deve permitir que o usuário selecione simultaneamente:

* uma empresa;
* várias empresas;
* todas as empresas;

e também selecione independentemente quais tipos de documentos deseja processar.

Exemplo:

Empresas:

☑ Empresa A
☑ Empresa B
☑ Empresa C
☐ Empresa D

Documentos:

☑ NF-e
☐ NFC-e
☑ CT-e
☐ CT-e OS
☑ NFCom

Período:

01/01/2026 até 31/01/2026

O sistema deve então utilizar automaticamente as fontes disponíveis para obter os documentos solicitados.

---

# 2. OBJETIVO PRINCIPAL

Eliminar a necessidade de acessar individualmente portais fiscais ou sistemas de terceiros para baixar XMLs das empresas do escritório.

O programa deverá centralizar:

1. cadastro de empresas;
2. certificados digitais;
3. consultas aos Web Services fiscais;
4. armazenamento de XML;
5. controle de NSU;
6. recuperação histórica;
7. identificação de documentos faltantes;
8. exportação organizada;
9. pesquisa de documentos;
10. auditoria do acervo.

O usuário final não deve precisar conhecer NSU, SOAP, schemas XML, endpoints ou regras técnicas.

A interface deve ser simples.

O usuário escolhe:

**empresa + período + documento**

e o sistema resolve tecnicamente a consulta.

# 3. PRINCÍPIOS DO PROJETO

## 3.1. Segurança

Dados fiscais e certificados são extremamente sensíveis.

Priorizar armazenamento local.

Nunca salvar senha de certificado em texto puro.

Certificados A1 devem ser protegidos utilizando recursos seguros do Windows.

Preferencialmente utilizar:

* Windows DPAPI;
* Windows Credential Manager;
* Windows Certificate Store;

ou mecanismo equivalente seguro.

Não registrar senhas em logs.

Não registrar tokens secretos em logs.

Nunca enviar certificado digital para serviços externos, exceto quando isso for tecnicamente indispensável e explicitamente configurado pelo administrador.

Toda comunicação externa deverá utilizar HTTPS/TLS.

---

## 3.2. Arquitetura modular

Não acoplar o programa diretamente a apenas uma API.

Criar uma arquitetura baseada em provedores/adaptadores.

Exemplo conceitual:

```text
IDocumentProvider

SefScProvider
NfeDistribuicaoNacionalProvider
CteProvider
NfceProvider
NfcomProvider
HistoricalRecoveryProvider
LocalArchiveProvider
```

Dessa forma, futuramente poderemos substituir ou acrescentar fontes sem reescrever o programa.

# 10. CONTROLE DE NSU

O usuário não deverá trabalhar manualmente com NSU.

O sistema deverá manter internamente o último NSU processado para:

```text
Empresa
+
Tipo de documento
+
Provider
```

Exemplo:

```text
Empresa ABC

NF-e
Último NSU:
000000000004285123

Última sincronização:
21/09/2026 20:14
```

Criar tabela específica para sincronização.

Não reiniciar NSU desnecessariamente.

Não solicitar repetidamente documentos já processados.

Implementar controle transacional:

somente atualizar o último NSU depois que a resposta for processada corretamente.

# 49. EXPERIÊNCIA DO USUÁRIO

O usuário do programa será profissional de contabilidade, não desenvolvedor.

Nunca mostrar mensagens como:

```text
NullReferenceException
HTTPClient TaskCanceled
XMLNode not found
```

Mostrar:

```text
Não foi possível consultar a SEFAZ.

Motivo:
tempo limite da conexão.

O sistema tentará novamente.
```

Permitir:

```text
Ver detalhes técnicos
```

para suporte.

---

# 50. NÃO FAZER

Não utilizar scraping de portal como mecanismo principal.

Não depender de CAPTCHA.

Não automatizar navegador se existir Web Service oficial.

Não salvar certificados de forma insegura.

Não armazenar senhas em código.

Não ignorar regras de consumo da SEFAZ.

Não considerar consulta pública como API.

Não usar endpoints não documentados sem necessidade.

Não vincular todo o sistema a um único fornecedor comercial.

Não apagar XML automaticamente.

Não sobrescrever arquivos sem controle.

Não inventar informações fiscais quando um XML estiver incompleto.

# 60. REGRA MAIS IMPORTANTE

O sistema deve possuir um único acervo central.

Independentemente da origem:

```text
SEF/SC
Ambiente Nacional
API histórica
XML importado
ZIP antigo
ERP
```

depois que o XML entra no WGS DF-e Manager, ele passa a fazer parte do mesmo acervo.

O usuário não deve precisar saber de qual fonte veio para utilizá-lo.

A origem deve ficar registrada somente para auditoria.

# 63. CERTIFICADO DO ESCRITÓRIO X CERTIFICADO DO CLIENTE

O sistema deverá suportar os dois conceitos.

Exemplo:

```text
Certificado do escritório/contador
```

para serviços que autorizem consulta através do vínculo contábil.

E:

```text
Certificado próprio do cliente
```

para serviços que exijam certificado do participante do documento.

Não presumir que todo provider aceita o certificado do contador.

Cada provider deverá declarar seu requisito.

# 65. PRIMEIRA TAREFA DO AGENTE DE DESENVOLVIMENTO

Antes de começar a implementar Web Services fiscais:

1. analisar este documento integralmente;
2. analisar os arquivos técnicos fornecidos pelo usuário;
3. identificar os layouts e protocolos;
4. propor a estrutura da solution;
5. definir as entidades iniciais;
6. criar arquitetura de providers;
7. implementar banco e camada de domínio;
8. implementar parser das chaves;
9. implementar importação do acervo;
10. somente então iniciar integração real com SEFAZ.

Não iniciar criando centenas de linhas de SOAP diretamente na interface gráfica.

# 67. RESULTADO ESPERADO

Queremos construir uma ferramenta profissional de gestão de documentos fiscais eletrônicos que inicialmente resolva uma necessidade interna real do escritório.

Ela deverá combinar:

**simplicidade para o usuário**

com

**arquitetura robusta por baixo**.

A aplicação deverá ser capaz de crescer de:

```text
Ferramenta interna da WGS
```

para:

```text
Produto comercial de gestão e recuperação de DF-e para escritórios contábeis
```

sem exigir uma reconstrução completa do sistema.

Prioridades, nesta ordem:

1. integridade fiscal;
2. segurança;
3. confiabilidade;
4. recuperação correta;
5. organização do acervo;
6. facilidade de uso;
7. desempenho;
8. possibilidade de expansão comercial.

Comece agora estruturando o projeto, propondo a arquitetura inicial e implementando a **FASE 1 — Fundação**, sem pular etapas e sem inventar endpoints ou regras fiscais que não estejam documentados.
